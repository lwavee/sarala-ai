# Sarala AI — Authentication & Identity Architecture (Task 1.1)

## 1. Architectural Overview

Sarala AI utilizes **Supabase Auth** as its canonical identity and authentication layer. All authentication flows (Signup, Login, Session Management, Logout, Token Issuance) are managed by Supabase Auth. The application identity of every user is anchored to `auth.users.id` (UUID).

```
   USER
     │
     ▼
SUPABASE AUTH (Email / Password)
     │
     ▼
AUTHENTICATED SESSION & JWT ACCESS TOKEN
     │
  ┌──┴───────────────────────────────────────────────────────┐
  ▼                                                          ▼
FRONTEND (Next.js)                                 BACKEND (FastAPI)
- Browser-safe Supabase Client                     - Token Verification (Supabase / HMAC / JWK)
- Centralized AuthContext & useAuth()              - Depends(get_current_user)
- Zero-Flash Profile Loading                       - Depends(get_current_admin)
- Dynamic User Greeting                            - Server-Side Role Enforcement (403 Forbidden)
- Role-Guarded UI Navigation                       - Never Trust Client-Supplied user_id or role
  │                                                          │
  └──────────────────────────┬───────────────────────────────┘
                             ▼
                 SUPABASE DATABASE & RLS
                 - auth.users (Credentials & Auth Engine)
                 - public.profiles (Foreign Key -> auth.users.id)
                 - Strict Row-Level Security Isolation
```

## 2. Canonical Identity & Profile System

### 2.1 Identity Hierarchy
- **Canonical ID**: `auth.users.id` (UUID generated by Supabase Auth).
- **Prohibited Identities**: Email, username, nickname, or frontend-generated random IDs are strictly prohibited from serving as primary foreign keys or canonical identities.
- **Application Profile**: Stored in `public.profiles`, linked to `auth.users` via a cascade foreign key:
  ```sql
  CREATE TABLE public.profiles (
    id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
    email TEXT UNIQUE NOT NULL,
    role TEXT NOT NULL DEFAULT 'user' CHECK (role IN ('user', 'admin')),
    full_name TEXT NOT NULL DEFAULT '',
    nickname TEXT DEFAULT '',
    avatar_url TEXT DEFAULT '',
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
  );
  ```

### 2.2 Automatic Profile Creation
A PostgreSQL trigger on `auth.users` automatically provisions the corresponding `public.profiles` row upon signup:
```sql
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO public.profiles (id, email, full_name, nickname, role, is_active)
  VALUES (
    NEW.id,
    NEW.email,
    COALESCE(NEW.raw_user_meta_data->>'full_name', NEW.raw_user_meta_data->>'name', split_part(NEW.email, '@', 1)),
    COALESCE(NEW.raw_user_meta_data->>'nickname', ''),
    'user',
    TRUE
  )
  ON CONFLICT (id) DO UPDATE SET email = EXCLUDED.email;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

### 2.3 Resilient Profile Recovery
If an authenticated Supabase user exists without a `public.profiles` row (e.g. if the user was provisioned externally or prior to trigger creation), both the frontend `AuthContext` and backend `get_or_create_profile()` implement self-healing creation:
- Automatically creates `public.profiles` with `role = 'user'`.
- Prevents crashes or blank screens.
- **Crucial Rule**: Self-healing never assigns `admin` privileges.

## 3. Role System & Privilege Escalation Prevention

### 3.1 Roles Supported
There are only two roles:
1. `user`: Normal user with access to chat, memory, and personal settings.
2. `admin`: Administrator with access to AI training, document ingestion, and analytics.

### 3.2 Server-Controlled Security Rules
- **No Client Privilege Granting**: The client can never grant itself or select `role = 'admin'`. New users always receive `role = 'user'`.
- **Database-Enforced Authorization**: The backend independently verifies the profile's role directly from Supabase / database queries.
- **Database Trigger Lock**: A PostgreSQL trigger `prevent_self_role_escalation` aborts any client-initiated UPDATE on `profiles` that modifies `role` or `is_active` unless the caller has admin status:
  ```sql
  CREATE TRIGGER trigger_prevent_role_escalation
    BEFORE UPDATE ON public.profiles
    FOR EACH ROW EXECUTE FUNCTION public.prevent_self_role_escalation();
  ```

### 3.3 Avee Administrator Account Configuration
- The administrator account (Avee) is defined strictly via the database role:
  `profiles.role = 'admin'`
- **No Hardcoded Passwords**: Neither the frontend nor the backend stores or compares passwords.
- **No Hardcoded Email Bypass**: Security logic does not perform `if email == 'loharavee@gmail.com'` to grant backend access. Access is determined purely by `current_user.role == 'admin'`.
- **Initial Setup**: The admin account is created via Supabase Auth (or Supabase dashboard), and the role is set to `'admin'` directly in `public.profiles`.

## 4. Authentication Flows

### 4.1 Signup Flow
1. User enters Email, Password, Full Name, and optional Nickname.
2. Frontend calls `supabase.auth.signUp({ email, password, options: { data: { full_name, nickname } } })`.
3. Supabase Auth creates `auth.users` row and fires `on_auth_user_created` trigger.
4. Profile row is inserted with `role = 'user'` and `is_active = TRUE`.
5. Frontend receives session, establishes `user`, fetches `profile`, and updates centralized state.

### 4.2 Login Flow
1. User enters Email and Password.
2. Frontend calls `supabase.auth.signInWithPassword({ email, password })`.
3. Supabase verifies password securely using bcrypt/argon2 hashing.
4. Supabase returns JWT access token and refresh token.
5. Frontend fetches authenticated profile from `public.profiles`.
6. Central state is updated: `isAuthenticated = true`, `isAdmin = (role === 'admin')`.

### 4.3 Logout Flow
1. User clicks Logout.
2. Frontend calls `supabase.auth.signOut()`.
3. Supabase invalidates local session tokens.
4. Central auth state immediately clears `user = null`, `profile = null`, `role = null`, `isAuthenticated = false`.
5. UI resets: Personalized greeting reverts from `Hello <Name> 👋` to `Hello 👋`.
6. Protected pages (like `/admin`) immediately lock and display 403 / Login screen.

### 4.4 Session Persistence & Restoration
- Supabase automatically persists the authenticated session in `localStorage` under Supabase client key.
- On browser reload, `supabase.auth.getSession()` and `supabase.auth.onAuthStateChange()` restore the session without requiring re-login.
- Auth state initializes in `loading = true` to prevent UI flash (e.g. never flashing "Hello Avee" to Rahul). Once restored, `loading = false` and the true identity is rendered.

## 5. Frontend Centralized State (`useAuth`)

All pages, components, and drawers consume a single unified hook:
```typescript
import { useAuth } from "@/context/AuthContext";

const { 
  user,            // Supabase User object (auth.users.id, email, etc.)
  session,         // Supabase Session (access_token, expires_at)
  profile,         // Application Profile (full_name, nickname, role, is_active)
  role,            // 'user' | 'admin' | null
  isAuthenticated, // boolean
  isAdmin,         // boolean (role === 'admin')
  loading,         // boolean (true during initial session restore)
  login,           // async (email, password) => { success, error }
  signup,          // async (email, password, name, nickname) => { success, error }
  logout           // async () => void
} = useAuth();
```

## 6. Backend API Authentication (FastAPI)

### 6.1 Token Verification Dependency
Endpoints requiring authentication declare `Depends(get_current_user)` or `Depends(get_current_admin)` from `backend.core.auth`:

```python
from fastapi import APIRouter, Depends
from core.auth import CurrentUser, get_current_user, get_current_admin

# Protected User Route (Requires valid Supabase Bearer token)
@router.get("/api/auth/me")
async def get_my_profile(current_user: CurrentUser = Depends(get_current_user)):
    return {
        "id": current_user.id,
        "email": current_user.email,
        "role": current_user.role,
        "full_name": current_user.full_name
    }

# Admin-Only Route (Enforces role == 'admin' -> 403 Forbidden on non-admin)
@router.post("/api/admin/training")
async def create_training(current_admin: CurrentUser = Depends(get_current_admin)):
    ...
```

### 6.2 Never Trust Frontend user_id
Incoming HTTP requests cannot spoof identity:
- Chat, settings, and memory endpoints extract the user ID exclusively from the verified token (`current_user.id`).
- Any `user_id` passed in request payloads or URL parameters is strictly ignored or verified against `current_user.id`.

### 6.3 Account Status Enforcement
If a user has `is_active = FALSE` in `public.profiles`:
- `get_current_user` raises `HTTP 403 Forbidden` ("Account has been disabled").

## 7. Row Level Security (RLS) Policies

All tables have RLS enabled:

| Table | Policy Name | Permitted Operation | Condition |
|---|---|---|---|
| `profiles` | Users can view own profile or admin views all | SELECT | `auth.uid() = id OR admin` |
| `profiles` | Users can update own profile | UPDATE | `auth.uid() = id` (role locked by trigger) |
| `conversation_metadata` | Users manage own conversations | ALL | `auth.uid() = user_id` |
| `user_preferences` | Users manage own preferences | ALL | `auth.uid() = user_id` |
| `memories` | Users manage own memories | ALL | `auth.uid() = user_id` |
| `training_items` | Read active training items | SELECT | `is_active = TRUE` |
| `training_items` | Admin write access | INSERT, UPDATE, DELETE | `profiles.role = 'admin'` |
| `knowledge_documents` | Admin write access | ALL | `profiles.role = 'admin'` |

## 9. Security Audit & Incident Prevention

1. **No Plaintext Passwords**: Legacy plaintext passwords have been purged from `users.json`, `DEFAULT_USERS`, and memory stores. All password authentication is handled by Supabase Auth with bcrypt hashing.
2. **Sanitized Logs**: Passwords, raw JWT access tokens, and API secret keys are never emitted in stdout, stderr, or application log files.
3. **Graceful Fallbacks**: If Supabase network connectivity is temporarily unavailable or in local offline mode, the system emits clean user-friendly alerts without crashing or dumping stack traces.
